# v0.5.0 — Endpoint Management UX

v0.5.0 is a minor release that turns `/litellm-endpoints` from an activation-only toggle into the complete management center for globally configured LiteLLM endpoints. Endpoints can now be added, edited and deleted from the terminal TUI instead of by hand-editing the config file.

## Added

`/litellm-endpoints` now supports the full management chain:

- view every configured endpoint with its activation and credential state,
- add an endpoint by entering an Endpoint ID and a Base URL,
- edit an endpoint's Base URL,
- delete an endpoint,
- activate / deactivate an endpoint (individually, or all at once),
- connect an API Key, replace an existing API Key, and disconnect an API Key.

Every choice, confirmation and text entry uses OpenCode's native `select` / `confirm` / `prompt` dialogs, so keyboard and mouse handling stay with the host. A stored API Key is never displayed back.

## Behavior worth knowing

- A newly added endpoint starts **inactive and not connected**. Adding it never activates it, so nothing new appears in the model selector until you activate it and connect a key.
- **Endpoint IDs cannot be renamed.** The ID is read-only in the edit flow; it is a stable slug that identifies the endpoint's credential, snapshot and failure domain. To rename, add the new endpoint and delete the old one.
- **Credentials and activation are independent.** Connecting a key does not activate an endpoint, and disconnecting a key does not deactivate it. Inactive endpoints still accept Connect / Replace / Disconnect.
- **Deactivate keeps the credential and the discovery snapshot.** Deactivation unregisters the runtime provider and stops its discovery loop; re-activating resumes discovery without re-entering a key.
- **`/connect` keeps working and shares one credential state** with the management UI. Both entry points report the same Connected state, and the provider uses the same stored key.
- **Legacy single-endpoint setups migrate safely.** If the address was entered through `/connect` rather than the config file, the internal `default` endpoint stays fully manageable: the plugin asks for confirmation once and moves the connected address (and top-level `protocolOverrides`) into `options.endpoints.default`, keeping the integration ID, credential and activation unchanged. For Delete the migration is part of the final delete confirmation, so cancelling changes nothing at all. Adding a second endpoint performs the same migration after confirmation.
- **Delete is explicit and complete.** It requires confirmation, and a confirmed delete removes the endpoint definition, its activation entry, its stored credential and its persisted discovery snapshot, then unregisters the provider. Other endpoints are untouched. Re-adding a deleted ID starts clean — inactive, not connected, no restored models.
- **Ordinary UI edits are non-destructive.** The one canonical plugin-options config file (`plugins[].options.endpoints` in the file that declares this plugin) is rewritten atomically and conflict-checked, so JSONC comments, formatting, unknown endpoint fields and unrelated top-level settings such as `pollInterval` and `contextTierCap` all survive. If the file cannot be parsed as JSONC, or the running options come from inline/project configuration instead of that file, Add / Edit / Delete are refused with an explanation while activation and credential management keep working.

## Still configured by hand

The management UI intentionally does not expose the remaining advanced settings:

- `protocolOverrides`,
- `pollInterval`,
- `contextTierCap`.

Hand-editing the config file is still supported, and the management center shows the file's real state on its next invocation without restarting OpenCode.

The management center depends on the terminal TUI. Desktop / Web clients do not load the TUI plugin; use the config file and `/connect` there.

## Real OpenCode 2.0.16 E2E coverage

The permanent real-host gate exercises the complete management chain against a real host:

1. install the exact candidate Git commit through OpenCode's own plugin installer,
2. start a real OpenCode 2.0.16 server and terminal client,
3. open the real `/litellm-endpoints` management dialog,
4. add an endpoint and assert it stays inactive and not connected,
5. connect an API Key and activate it, verifying provider and model visibility,
6. edit the Base URL and confirm the running provider uses the new address,
7. deactivate and assert the credential and snapshot are retained,
8. delete an endpoint and assert the full cleanup,
9. migrate a legacy single-endpoint configuration into full management after confirmation.

The E2E uses isolated HOME/XDG directories and local fake LiteLLM servers only; it does not read user configuration or real credentials.

## Install / upgrade

Follow the latest stable main:

```sh
opencode plugin update "github:rpchen/opencode-litellm-provider"
```

Or pin v0.5.0:

```sh
opencode plugin add github:rpchen/opencode-litellm-provider#v0.5.0
```

After upgrading from v0.4.3, fully restart OpenCode so both the server plugin and terminal TUI load the same candidate. Existing configs are not rewritten by the upgrade; you keep the same endpoints, credentials and activation state.
