# v0.7.0 — Trustworthy Model Capability Publication

v0.7.0 is a minor release: a model discovered from LiteLLM is now published to OpenCode only when its capability metadata is trustworthy. Incomplete or invalid models no longer masquerade as normal models, metadata outages have an explicit and explainable recovery path, and "I know about the gaps and still want to use it" becomes an action you take yourself.

## Highlights

- A trustworthy publication gate sits between discovery and model registration.
- Incomplete / invalid models are blocked instead of silently published.
- `models.dev` / metadata outages fall back to last-known-good (LKG) data with explicit rejection rules.
- Explicit degraded acceptance via `/litellm-accept-degraded`.
- Reasoning models without selectable levels are still marked as reasoning.
- Diagnostics and the TUI show publication state, provenance and failure reasons.
- Endpoint activation behaviour is unchanged.

## Trustworthy publication

Discovery and registration are now separated by a publication partition. A model is registered as a normal model only when the capability information needed to use it correctly — context window, output limit, tool calling, reasoning — is complete and trustworthy:

- unknown capability is no longer reported as `false` or `true`;
- models with `context <= 0` or `output <= 0` are never registered;
- incomplete metadata does not fake a complete configuration — the model is classified as incomplete instead.

In practice: a normal model in `/models` means its capability data is actually trustworthy, not that a plausible-looking configuration was assembled from defaults.

## Metadata outage and LKG

- When metadata retrieval fails (timeout, 5xx, unreachable network), a still-trustworthy historical complete snapshot (LKG) keeps the model available, labelled as LKG with its source and data age;
- LKG has no fixed TTL: age alone never invalidates a snapshot;
- when a fresh live fact conflicts with an older snapshot, the stale LKG is rejected rather than overriding newer data;
- with no trustworthy data at all, a model is never quietly published as normal — it lands in the incomplete state, waiting for an explicit decision.

This covers `models.dev` outages as well: `models.dev` only supplements LiteLLM data, and a `models.dev` outage never invents or drops models.

## Explicit degraded acceptance

```text
/litellm-accept-degraded <model-id>          (multi-endpoint: <endpoint-id> <model-id>)
```

- You must run the command yourself — the plugin never accepts degraded publication on your behalf;
- an accepted model stays marked as degraded: degraded is **not** fully configured, and `/litellm-diagnostics` keeps listing the remaining gaps;
- acceptance takes effect on the next discovery refresh and must be repeated after a restart;
- models with unrecognised identity, invalid metadata or no match (invalid / ambiguous) are rejected — the command does not report success for them.

## Publication RPC

Publication state is exposed through the plugin's internal publication RPC: diagnostics, the audit command and the TUI all read the same partition (publishable / degraded / LKG / blocked) from one source, so what you see in the TUI card, in `/litellm-diagnostics` and in the audit export cannot drift apart. The RPC also carries the "accepted degraded" event that re-publishes an explicitly accepted model on the next refresh.

## Diagnostics and TUI visibility

`/litellm-diagnostics` now shows the publication partition per endpoint:

- **available** — complete, trustworthy capability data;
- **incomplete** — which capability fields are missing;
- **invalid** — identity or metadata cannot be trusted; cannot be accepted normally;
- **LKG** — running from a historical complete snapshot, with source and data age;
- **degraded** — explicitly accepted, with the remaining gaps;
- each non-normal state carries its provenance and failure reason, so you can tell a network failure apart from missing upstream fields or an identity match failure.

The diagnostics card in the terminal TUI renders the same state; Desktop / Web clients that do not load TUI cards simply do not show the card. Diagnostics remain read-only: no model requests, no API key or LiteLLM address in the output.

## Reasoning models

- A model that supports reasoning but exposes no selectable thinking levels is still correctly marked as reasoning;
- "no levels" does not mean "no reasoning" — `/models` and the reasoning metadata no longer drop such models from the reasoning category.

## Endpoint activation unchanged

Endpoint activation is untouched in this release: endpoints can still be enabled/disabled independently, an inactive endpoint stops publishing its provider immediately, and activation state survives upgrades. Only *how* a discovered model is published changed.

## Real OpenCode 2.0.16 verification

Before release, the candidate must pass the normal delivery CI plus the dedicated **Real OpenCode 2.0.16 E2E** job: OpenCode's own plugin installer installs the exact candidate Git commit against isolated HOME/XDG and local fake LiteLLM servers, then verifies command registration, provider/model visibility, publication partition (incomplete/invalid blocked, LKG substitution, degraded accept/reject), diagnostics and startup Runtime Identity, and TUI rendering — without touching `.git`, your configuration or real credentials.

## Install / upgrade

Follow the latest stable main:

```sh
opencode plugin update "github:rpchen/opencode-litellm-provider"
```

Or pin v0.7.0:

```sh
opencode plugin add github:rpchen/opencode-litellm-provider#v0.7.0
```

After upgrading from v0.6.0, fully restart OpenCode (`opencode reload` or a new process) so both the server plugin and the terminal TUI load the same candidate. Existing configs, credentials and activation state are not rewritten. On first discovery after the upgrade, models are re-evaluated against the publication gate: a model that previously "looked normal" may now show up as incomplete or require explicit degraded acceptance — that is intended.
