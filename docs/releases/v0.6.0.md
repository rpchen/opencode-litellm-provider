# v0.6.0 — Runtime Identity

v0.6.0 is a minor release that gives every running plugin artifact its own immutable identity. When reporting an issue, you no longer have to guess which Git commit or branch is running — read the Runtime Identity instead.

## Runtime Identity

The running artifact now reports three fields:

- `Plugin Version`: the plugin version (`0.6.0`),
- `Artifact Digest`: the deterministic SHA-256 identity of the artifact,
- `Core Commit`: the bundled `litellm-discovery-core` commit (`8e155e0efe90f1e9e7c8e973239c206a97011477`).

Find it in three places, all reading the same source:

- `/litellm-diagnostics` ends with a `Runtime Identity` block (short form),
- `/litellm-audit-export` includes the full `runtimeIdentity` object in the exported JSON,
- the plugin startup log prints one `LiteLLM Runtime Identity plugin=… artifact=… core=…` line.

```text
Runtime Identity

Plugin Version   0.6.0
Artifact         e5aa34e0
Core Commit      8e155e0e
```

When reporting an issue, include the Runtime Identity section from `/litellm-diagnostics` or the audit export.

## Real OpenCode 2.0.16 E2E coverage

The permanent real-host gate installs the exact candidate commit through OpenCode's own plugin installer and verifies, against isolated HOME/XDG and local fake LiteLLM servers, that diagnostics show the candidate short identity, the audit export carries the full identity, and the startup log records the same identity — without touching `.git`, user configuration or real credentials.

## Install / upgrade

Follow the latest stable main:

```sh
opencode plugin update "github:rpchen/opencode-litellm-provider"
```

Or pin v0.6.0:

```sh
opencode plugin add github:rpchen/opencode-litellm-provider#v0.6.0
```

After upgrading from v0.5.0, fully restart OpenCode so both the server plugin and terminal TUI load the same candidate. Existing configs are not rewritten by the upgrade; you keep the same endpoints, credentials and activation state.

## Verification

Before release, the release candidate must pass the normal delivery CI and the dedicated **Real OpenCode 2.0.16 E2E** job on `main`.

The tag-triggered Release workflow then re-verifies:

- release version / manifest / lockfile consistency,
- release metadata consistency,
- OpenSpec closure,
- committed distribution at its fixed Core provenance,
- test cache integrity and immutable verification,
- delivery integrity, typecheck and all unit tests,
- TUI render checks,
- clean distribution rebuild,
- package installation from both tarball and Git tag,
- generated release tarball and SHA-256 checksum,
- downloaded published assets and extracted `dist` byte-for-byte equivalence.

Committed discovery Core remains pinned to `8e155e0efe90f1e9e7c8e973239c206a97011477`.
