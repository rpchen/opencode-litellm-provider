# v0.8.0 — Endpoint 状态现在更准确

v0.8.0 是一个 minor 版本：endpoint 状态不再只是一个"启用/未启用"开关。配置表达你的意图，OpenCode 运行时表达现实，UI 诚实地展示两者，而 `/models` 只承诺现实。凭据状态也更精确："已保存 API Key"不再被错误地说成"已连接"。

## Highlights

- endpoint 状态从单一 boolean 升级为七个精确状态，能解释"为什么 `/models` 是空的"。
- 应用失败不再偷偷把配置改回去；UI 明确显示"未生效"或"出错"。
- Credential 状态不再称为"已连接/未连接"，改为"已保存 API Key / 未保存 API Key / API Key 来自环境变量 / 凭据状态未知"。
- 配置非法的 endpoint 不再从管理界面消失，修复路径可见。
- 新增 **重新应用（Retry）**：临时失败无需"停用 → 再启用"。
- `/models` 只发布当前真正 apply 成功的 endpoint 的模型。
- `/litellm-diagnostics <id>` 对任意状态都输出完整 detail。
- 管理中心、diagnostics 与 OpenCode provider/model runtime 读取同一份 canonical state，不再各自拼状态。

## Endpoint 状态现在更准确

每个 endpoint 的状态由四个独立维度派生：**期望状态**（你在 `options.endpoints` + activation 中要求的）× **配置**（`baseUrl` 定义是否合法）× **凭据**（是否已保存 API Key）× **Runtime**（当前进程里该 endpoint 是否真正被应用成功）。七个用户可见状态：

| 状态 | 含义 | 下一步 |
|---|---|---|
| `已启用 · 已生效` | 启用 + 配置合法 + 有凭据 + 本次进程 apply 成功 | 正常使用 `/models` |
| `已启用 · 需要认证` | 启用但没有保存 API Key | 在详情选 **连接 API Key** 或 `/connect` |
| `已启用 · 未生效` | 启用且配好凭据，但本进程尚未 apply 成功一次 | 在详情选 **重新应用** |
| `已启用 · 出错` | 最近一次 apply 失败（网络/认证/解析等） | 查看 `/litellm-diagnostics <id>`，修复后 **重新应用** |
| `已启用 · 配置非法` | `baseUrl` 等定义非法，不会被注册 | 在详情选 **修改 Base URL** 修复 |
| `未启用` | 配置合法但已停用 | 在详情选 **启用** |
| `未启用 · 配置非法` | 既停用又配置非法；仍然可见可修复 | 先修复，再视需要启用 |

之前 apply 失败时 TUI 仍显示"已启用"却无法解释 `/models` 为空；现在每个状态都带有明确的下一步。

## 配置表达意图，Runtime 表达现实

你在管理中心做的启用/停用就是你的意图，持久化保存在 host plugin storage（`litellm.activation.v1`），**不会**因为 runtime 临时失败而被偷偷改回：

- 启用成功但 apply 失败时，activation 里仍是"已启用"，TUI 显示 `已启用 · 未生效` 或 `已启用 · 出错`，从不说谎成功，也从不自动回滚；
- runtime 恢复（手动 **重新应用**、`endpointRpc.trigger` 或下一轮轮询成功）后状态回到 `已生效`。

## Credential 状态更准确

凭据状态只描述"是否已保存 API Key"，不再把它说成连接状态：

- **已保存 API Key** — 凭据已保存到 OpenCode 凭据存储（与 `/connect` 同一份）
- **API Key 来自环境变量** — legacy `default` 使用环境凭据
- **未保存 API Key** — 尚无凭据
- **凭据状态未知** — 凭据存储无法读取时的诚实表达

**"已保存"不蕴含 endpoint 可达**：要确认可达，看 `Runtime` 是否"已生效"。"连接 API Key" 仍作为操作名称（在 endpoint 详情里执行），它只保存 key，不改变启用状态。内部 discovery 状态里的"未连接"字样也已改为"尚未发现 LiteLLM"，避免与凭据语义混淆。

## Invalid endpoint 不再消失

`baseUrl` 非法（非 http(s)、带用户信息等）的 endpoint 定义以前会被 `parseOptions` 静默丢弃，从管理界面和 diagnostics 里彻底消失。现在它们：

- 继续出现在 `/litellm-endpoints`、endpoint 详情与 `/litellm-diagnostics`；
- 明确显示 `已启用 · 配置非法` 或 `未启用 · 配置非法` 并给出原因；
- 永远不会注册 provider/模型（不发起网络请求）。

修复方式：在详情里选 **修改 Base URL**；输入框与运行时使用同一条校验规则（共享 core 的 `normalizeLiteLLMURL` / `isEndpointID`），改对即可生效。

## 新增"重新应用"

`已启用 · 未生效` / `已启用 · 出错` 的 endpoint，在详情里新增 **重新应用**（服务端由 `endpointRpc.trigger` 驱动）：只对该 endpoint 触发一次强制 refresh，无需"停用 → 再启用"，也不会改写持久化激活状态。disabled / invalid / 需要 认证 或状态已是 `已生效` 时不会出现该操作（服务端也会用 `code=invalid-state` 拒绝）。

## /models 只承诺真实运行状态

`/models`（OpenCode 模型选择器、`opencode models`）只列出**当前进程里真正 apply 成功**的 endpoint 的模型。以下状态不会出现在 `/models`（历史快照也不会让它们继续显示）：

- disabled / invalid configuration
- needs authentication
- not applied（本进程尚未成功应用）
- error（最近一次 apply 失败）
- stale snapshot only（持久化快照只用于诊断回放，不伪装成可调用模型）

`/models` 里看到的 LiteLLM 模型，就是此刻真的注册在 OpenCode provider/model runtime 里的模型。

## Diagnostics 一致性

`/litellm-diagnostics <id>` 对 **disabled / invalid / needs-auth / not-applied / error / active** 全部输出完整 detail：期望状态、配置（合法/非法 + 原因）、凭据、Runtime（已生效/未生效/出错 + 分类）、当前注册模型数、最近成功发现时刻——不再退化为占位信息。TUI 管理中心列表、详情标题、diagnostics 卡片与真实 provider 注册读取同一份 canonical state；审计导出（`/litellm-audit-export`）与对话反馈同源。

## Compatibility

- **无需迁移**：现有 endpoint 配置、凭据与启用状态不变，配置文件 / `litellm.activation.v1` / `litellm.discovery.snapshot.v1[.<id>]` 格式不变；
- 现有 valid endpoint 继续工作；
- 之前被静默隐藏的非法 endpoint 现在会**变得可见**（标记为"配置非法"并提示修复）——这是预期行为；
- 凭据从"已连接"改为"已保存 API Key"后，同一把 key、同一份 `/connect` 宿主凭据，无需重新连接。
